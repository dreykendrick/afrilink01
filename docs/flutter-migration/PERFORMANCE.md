# PART 17 — Performance, Caching & Mobile Stability

## 17.1 Caching
- **TanStack Query is installed and provides the app-root `QueryClient`, but with fully default options** (`new QueryClient()` — no `staleTime`, `gcTime`/`cacheTime`, `retry`, or `refetchOnWindowFocus` overrides) and it is **not actually used** for the main data flows in `Index.tsx`/dashboards (those use raw `useState`+`useEffect`+direct Supabase calls, refetching from scratch on every relevant view change — see STATE_MANAGEMENT.md §8.1/8.3). Practically, there is **no client-side query caching/deduplication today** for products, profile, stats, or affiliate links — a Flutter rebuild should decide deliberately whether to introduce real caching (e.g. equivalent to `staleTime`) rather than assume current parity requires none.
- **Workbox/service-worker caching** (via `vite-plugin-pwa`, configured in `vite.config.ts`) is the only real caching layer present:
  - `globPatterns: ["**/*.{js,css,html,ico,png,svg,webp,jpg,jpeg}"]` — precaches build output assets.
  - One `runtimeCaching` rule: Unsplash images (`https://images.unsplash.com/.*`) use `CacheFirst` with cache name `image-cache`, `maxEntries: 100`, `maxAgeSeconds: 604800` (7 days).
  - No runtime caching rule exists for Supabase API responses or product images hosted elsewhere (e.g. Supabase Storage) — only the specific Unsplash placeholder host is covered.
- `localStorage` acts as a lightweight cache for a few cross-session values (cart, affiliate code, active role, canonical app URL, i18next language) — see STATE_MANAGEMENT.md §8.9.

## 17.2 Lazy loading
- **Route-level code splitting:** none found — all pages (`Index`, `NotFound`, `ProductPage`, `OrderConfirmationPage`, `CheckoutConfirmPage`) are imported statically/eagerly in `App.tsx` (no `React.lazy`/`Suspense` for routes).
- **Image lazy loading:** `ProductCard.tsx` sets `loading="lazy"` on the product `<img>` tag — this is the only explicit lazy-loading directive found (native browser lazy-loading, not a custom IntersectionObserver component).
- **i18n locale bundles:** loaded eagerly, not lazily (all 3 languages always in the bundle — see CONFIGURATION.md §18.6).
- **Dashboards/views:** since `Index.tsx` renders all views from one component via conditional `if (view === ...)` blocks (not React Router route-based code splitting), all view components are part of the same bundle and are not code-split by route.

## 17.3 Image loading strategy & `URL.createObjectURL` cleanup
- Remote product images are plain `<img src=...>` tags pointing at either Supabase-hosted URLs (`image_url`/`image_urls` columns) or the hardcoded Unsplash fallback (see CONFIGURATION.md §18.4). No responsive `srcset`/`sizes`, no client-side resizing/compression before upload beyond what upload modals do.
- **Local file preview pattern** (used for avatar/logo/photo upload flows) consistently uses `URL.createObjectURL(file)` to generate an instant local preview, and — critically — **explicitly revokes the previous object URL with `URL.revokeObjectURL(...)` before creating a new one and/or after the upload completes**, to avoid leaking blob memory. This exact cleanup rule is applied in:
  - `src/components/dashboard/SettingsPage.tsx` (revokes before setting a new preview at line ~112, and again after successful save at line ~188/96).
  - `src/components/onboarding/AffiliateProfileSetup.tsx` (revokes previous avatar preview before setting a new one).
  - `src/components/onboarding/VendorProfileSetup.tsx` (revokes previous logo preview before setting a new one).
  - `src/components/dashboard/ProductImagesModal.tsx` (creates an object URL from a blob, then revokes it, likely after using it for a short-lived operation like triggering a download).
  - `src/components/auth/VerificationForm.tsx` creates a preview via `URL.createObjectURL` but was not confirmed in this pass to have a matching revoke call — worth auditing when porting, and in Flutter this whole pattern maps to: decode the picked file into an in-memory image/bytes for preview, and explicitly dispose/null-out the byte buffer once no longer needed or after upload, rather than leaving stale large buffers referenced by widget state.
  - **Rule for Flutter:** never leave a decoded image/blob-equivalent reachable from state after it's superseded by a new selection or after the upload completes — always dispose of the old one first.

## 17.4 Infinite scroll vs fixed queries
- **No infinite scroll is implemented anywhere.** All list data (marketplace products, vendor products, notifications, affiliate links) is fetched as one fixed query per load — see SEARCH.md §16.9 and STATE_MANAGEMENT.md §8.8 for exact pagination-state confirmation (none exists, aside from `useNotifications`'s hardcoded `.limit(20)` with no "load more").

## 17.5 Pagination
- Only `useNotifications` applies a limit (`20`), and even that has no follow-up page/cursor mechanism — it's a fixed cap, not true pagination. All other data fetches (products, vendor products, affiliate links) are unbounded `select('*')` queries. This is a known scalability gap (see §17.8).

## 17.6 Pull-to-refresh
- Implemented as a custom gesture component, `src/components/mobile/PullToRefresh.tsx` (touch-event based, not a library):
  - Tracks `pulling`, `refreshing`, `pullDistance` state and a `startY` ref.
  - Only begins tracking a pull if the scroll container's `scrollTop === 0` (i.e., already at the top) on `touchstart`.
  - Applies a `0.4` resistance multiplier to the raw vertical drag delta, capped at `maxPull = 120`px.
  - On `touchend`, if `pullDistance >= threshold` (`80`px) and not already `refreshing`, sets `refreshing = true`, pins the indicator at the threshold distance, awaits the provided `onRefresh()` promise, then resets both `refreshing` and `pullDistance` in a `finally` block (guaranteed reset even on error).
  - Visual indicator: a spinning `Loader2` icon inside a circular badge that scales/rotates proportionally to pull progress (`progress = pullDistance/threshold`, clamped to 1).
  - Used in two places in `Index.tsx`: wrapping the dashboard content (`onRefresh={handleRefresh}` → `fetchUserData()`) and the marketplace content (`onRefresh={handleMarketplaceRefresh}` → `fetchMarketplaceProducts()`); both are `disabled={dataLoading}` while a fetch is already in flight, preventing overlapping refreshes.
  - Flutter equivalent: `RefreshIndicator` reproducing the same threshold/disable-while-loading semantics (exact pixel thresholds are a UX design choice, not required to match exactly, but the *behavioral* contract — disable while loading, always reset state in a `finally`-equivalent — should be preserved).

## 17.7 PWA service worker / Workbox strategy
- `vite-plugin-pwa` with `registerType: 'autoUpdate'` — the service worker checks for updates and activates automatically without prompting the user to manually reload (paired with `skipWaiting: true` and `clientsClaim: true` in the Workbox config, which together mean a new service worker version takes control of all open tabs immediately rather than waiting for them to close/reload — an intentional "always latest" strategy, at the cost of potentially swapping code out from under an open tab mid-session).
- `cleanupOutdatedCaches: true` — old precache versions are purged automatically on activation.
- `importScripts: ['/sw-push.js']` — an additional hand-written service worker script (outside the Workbox-generated one) is imported for push-notification handling (`show notification on push event`, click-to-open logic) — this file lives outside the reviewed scope but its existence means push notifications are wired through the *browser* service worker, not a native-only mechanism; a Flutter rebuild would instead use native push (FCM/APNs) directly, so this specific file's logic (not just its existence) should be reviewed separately when implementing push in Flutter.
- `navigateFallbackDenylist: [/^\/~oauth/]` — ensures any `/~oauth...` path is never served the cached SPA shell as a fallback (must hit the network / real handler), relevant for OAuth redirect flows.
- Manifest fields (`theme_color`, `background_color`, icons, `display: 'standalone'`, `orientation: 'portrait'`, `start_url: '/'`, `scope: '/'`) drive "Add to Home Screen" / installed-PWA behavior; `usePWA.tsx` separately detects `display-mode: standalone` and `navigator.standalone` (iOS) to know if the app is already installed, and listens for the `beforeinstallprompt`/`appinstalled` browser events to offer a custom install prompt (`InstallPrompt` component, not reviewed in depth here).

## 17.8 Preloading
- No explicit `<link rel="preload">`/`prefetch` hints, no route/data prefetching-on-hover, and no image preloading strategy beyond the Workbox `CacheFirst` rule for Unsplash. The only "prefetch-like" behavior is `usePushNotifications`'s VAPID key caching in a `useRef` so it's fetched at most once per session, and the app URL caching in `localStorage`/in-flight promise dedup (`inFlight` variable in `appUrl.ts`) to avoid redundant `app-config` function calls when multiple callers request the canonical URL concurrently.

## 17.9 Mobile stability rules observed in code
- **`isMountedRef` guard pattern:** `AddProductModal.tsx` and `EditProductModal.tsx` both declare `const isMountedRef = useRef(true)`, set it `true` on mount and `false` in the cleanup function of a mount-only effect, and check `isMountedRef.current` before calling `setState` after any `await` (image upload, product create/update) — this prevents "setState on unmounted component" warnings/crashes if the user navigates away mid-upload. **This exact guard pattern should be replicated in Flutter** via `mounted` checks on `State` objects before calling `setState` after async gaps.
- **No base64-encoded images held in React state** were found in the reviewed files — image previews use `URL.createObjectURL` (a lightweight reference, not the raw bytes) rather than base64 data URIs, which keeps state objects small and avoids the classic "giant base64 string in state causes jank/OOM on low-end devices" anti-pattern. **Flutter parity rule:** prefer holding a `File`/byte-stream reference (or a decoded `ui.Image` only when actively needed for display) over storing base64-encoded strings in widget state, for the same memory/performance reasons.
- **Deferred role-fetching via `setTimeout(..., 0)`** in `useAuth.tsx`'s `onAuthStateChange` callback — this is a documented workaround to avoid a deadlock in the Supabase JS client when calling another Supabase method synchronously inside the auth callback. Flutter's `supabase_flutter` client does not have this exact deadlock issue, but the underlying principle — don't perform additional synchronous SDK calls inside an auth-state-change callback; defer to a microtask/next event loop tick — is worth preserving defensively.
- **`try/finally` for loading flags:** both `fetchUserData()` (`Index.tsx`) and the Push subscribe/unsubscribe methods wrap their async bodies in `try { ... } finally { setLoading(false) }`-style patterns, guaranteeing loading indicators clear even on error — a good pattern to preserve in Flutter's async state handling (e.g., always resetting a loading `bool` in a `finally` block or equivalent).
- **Recovery-lock ref pattern:** `Index.tsx`'s `recoveryLocked`/`isRecoveryLocked` refs guard against other effects overriding navigation during a sensitive flow (password recovery) — an example of using refs (not state) for values that must be read synchronously without triggering re-renders, and that must survive across multiple effects. Flutter equivalent: a plain instance field / `ValueNotifier` read synchronously by navigation guards, not something that needs to trigger a rebuild itself.

## 17.10 Known bottlenecks / gaps to address (not necessarily to fix, but to flag)
- **Unbounded product fetches:** the entire `products` table (filtered only by `status='approved'`) is fetched on every marketplace/landing view-entry with no pagination, limit, or server-side filtering by search term/category — this will not scale as the catalog grows; every keystroke in search re-filters the full in-memory array (see SEARCH.md §16.3).
- **No memoization** of `filteredProducts`/`categories` computations in `Index.tsx` — recomputed on every render of the large `IndexContent` component, not just when their true dependencies change (no `useMemo`).
- **Duplicate marketplace fetches:** `fetchMarketplaceProducts()` can be triggered redundantly — e.g. once by the `[view]` effect and again by `handleNavigate('marketplace')` explicitly calling it — with no request de-duplication/in-flight guard (unlike `getAppUrlAsync`'s `inFlight` promise pattern, which IS deduplicated).
- **All product/profile/stats data refetched from scratch** on every relevant view transition (no cache), meaning repeated navigation between `dashboard` ↔ `marketplace` ↔ `settings` re-runs full Supabase queries each time rather than reusing recently-fetched data — a prime candidate for real caching in the Flutter rebuild (e.g., a repository layer with in-memory TTL cache) even though it's not how the current app behaves.
- **Single-item checkout handoff limitation:** the external checkout only processes the first cart item at a time (`performMarketplaceCheckoutHandoff` explicitly documents this design limitation) — multi-item carts require repeated handoffs, which is a UX rough edge inherited from the current architecture, not a performance bug per se, but relevant context for anyone rebuilding checkout flow timing/loading states.
- **Service worker `skipWaiting`/`clientsClaim: true` combo** can occasionally cause an open tab's in-memory state to become inconsistent with newly-cached assets mid-session (a known trade-off of "auto update" PWA strategies) — not directly portable to Flutter (no service worker), but worth noting when designing the Flutter app's own update/versioning strategy (e.g., in-app update prompts) as the intended replacement behavior.
